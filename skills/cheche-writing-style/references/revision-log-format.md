# 逐页文字修改对照表 · 格式规范

这是 cheche 认可的交付格式（原话："你的对比表格式很好，记得复用"）。**每次改稿都用这一套，不要另创格式。**

## 用途

给领导 / 客户确认：**改了什么、在哪一页、为什么改**。让对方不必逐页翻文件，就能审完全部改动。

## 文件命名

```
<日期>-<项目名>-<原版本>→<新版本>-文字修改对照表.md
```
例：`2026-09-30-凯西经营大脑-v4b→v7-文字修改对照表.md`

## 结构（四节，顺序固定）

### 开头 · 总说明（一行）

> 全稿共修改 **N 处文案**（逐页 X 处 + 全文统一 Y 类 Z 处），另有 **k 处版式微调**。

数字必须能对上：N = X + Z。

### 一、全文统一修改

全稿一次性替换的项（组名、自称、图注、删除占位等）：

| # | 位置 | 原文 | 改后 | 处数 | 说明 |
|---|---|---|---|---|---|

- 「位置」写**覆盖范围**（如"封面、章节页 02、P09、P11 等 25 页"），不逐页罗列。
- 「处数」写实际命中次数。

### 二、逐页文字修改

一页一行；同页多项分多行：

| # | 页码 | 位置 | 原文 | 改后 | 说明 |
|---|---|---|---|---|---|

- 「位置」写**页内方位**（大标题／副题／正文第 2 段／右下角图注／页脚导航）。
- 「说明」写**为什么改**，不写"改得更好了"。三类措辞：
  统一自称 / 用词书面化 / 句式规范化。需要点明原意时补一句：
  > 「接着用」偏口语，改为「继续沿用」——语义不变，语气更书面。
- 本轮新增的改动可标 **②** 之类的记号，方便对方优先看这几行。

### 三、版式微调

只在确实动过版式时出现。写清页码、原位置、改后位置、原因（通常是"文字加长后遮挡"），附截图文件名更好。

### 四、本次未改动的内容

**这一节最重要**——主动写明没动什么，对方才放心：

- 标题（除非明确要求）
- 页面顺序与页面增删（按对方版本保留，未回滚）
- 配图数量与页数
- 章节页不印页码等体例约定
- 旧格式版本（PPTX / PDF）未同步

## 生成方式

用 `scripts/gen_revision_log.py`，一条命令完成**生成 + 强校验**。**这个脚本在本技能内，不依赖别的技能。**

### 入口一：有 `changes.json`（HTML 幻灯片改稿）

```bash
python scripts/gen_revision_log.py \
    --changes changes_v6.json changes_v7.json \
    --out "2026-09-30-项目名-v4b→v7-文字修改对照表.md" \
    --global-cats "组名,图注" \
    --verify 新文件.html
```

### 入口二：没有 `changes.json`（纯文字改稿）—— 手写一份清单就行

改 md / txt / docx 时没有 JSON，直接列一张改动清单：

```bash
python scripts/gen_revision_log.py \
    --pairs 改动清单.txt \
    --out "2026-09-30-项目名-v1→v2-文字修改对照表.md" \
    --verify 新文件.md
```

清单一行一条，列序固定，分隔符用 `||` 或制表符（也可以直接粘 Markdown 表格行）：

```
页码 || 位置 || 原文 || 改后 || 说明 || 处数(可选)
```

```
p22 || 正文第 2 段 || 原文…… || 改后…… || 句式规范化
ALL || 图注 || 沃橙团队出品 || —— || 删除占位
```

- 页码写 `-` / `ALL` / `全局` → 归入第一节「全文统一修改」；写 `p22` / `P22` / `22` → 归入第二节。
- 「改后」留空 = 整段删除，表里印成「（整段删除）」。
- 空行、`#` 注释行、Markdown 表格分隔行（`|---|---|`）自动跳过。

### 两个入口共用

- 多个 `--changes` 按顺序做**链式归约**：A→B（第一轮）、B→C（第二轮）合成 **A→C**，
  中间态不出现在表里；回到起点（A→B→A）判为净无改动，整条不入表。
  `--pairs` 排在 `--changes` 之后，同一处冲突时以手写清单为准。
- `--verify` 会解析表中每条「改后」文案，确认它能在新文件里命中。**这一步不能省。**
- 数据形态对不上时用逃生口兜住：`--drop-old`（上一轮改过、本轮撤销但不产出条目的）、
  `--fix "原文||改后"`（交叉引用文案这类需要接上的）。

也可以手写，但格式必须与本文件一致。**多轮改动合并成一份净结果表**（相对最初给用户的那一版），不要分成多份。

## 交付前强校验（必做）

解析表中每一条「改后」文案，确认它能在新文件中命中（先剥离 HTML 标签、归一化空白）：

```python
def norm(x):
    return re.sub(r'[\s\u3000]+', '', re.sub(r'<[^>]+>', '', x))

assert norm(新文案) in norm(新文件)
```

有一条命中不了，就是表或文件有错，**必须查清再交付**。
（例外：写「（整段删除）」这类条目天然命中不了，校验时应跳过。）
