# cheche 文风标准与改稿

## 概述

本技能回答一个问题：**这句话该怎么写。**

它只管**字词层**——禁用词、书面化、主语完整、自称统一、句式规范、术语保留。
它**不管**文件怎么改（那是 `cheche-html-deck-edit`），也**不管**方案怎么搭（那是 `cheche-proposal-writing`）。

**判据分三层优先级，指向不一致时序号小的赢：**

| 优先级 | 判据 | 回答 |
|---|---|---|
| 1 | **功能与语境** | 这段文字在这个位置干什么 |
| 2 | **个人文风** | 按我的偏好该怎么写（A/B/C 词表与白名单） |
| 3 | **通用规则** | 还有哪些通用 AI 痕迹要清 |

优先级为什么必要、通用规则在方案体裁上哪些适用哪些要重划豁免，见 `references/edit-discipline.md`。
第三层（通用规则）的**完整词面清单、逐条处置与实测依据**见 `references/ai-tells.md`。

| 你要做的事 | 用哪个技能 |
|---|---|
| 改文风、去 AI 味、审文案 | **本技能** |
| 出逐页修改对照表 | **本技能**（自带生成器，纯文字改稿不必依赖别的技能） |
| 把文字改动落回 HTML 幻灯片 | `cheche-html-deck-edit` |
| 从零写方案 / 大改结构 | `cheche-proposal-writing` |
| 检查幻灯片版式有没有被撑破 | `html-slide-overflow-qa` |

**本技能跨项目通用。** 规则是通用的，案例是具体的——文中引用的《凯西经营大脑》是**样本项目**，其中的品牌名、客户名只是例证。用到别的项目时先做下面的「项目变量」确认。

适用对象：对外方案与投标文件、客户汇报材料、HTML/PPT 幻灯片、培训课件、公众号长文中的正式段落。

## 项目变量（开工前先确认，勿沿用上一项目）

这几项每个项目都可能不同，**不要从案例里照抄**：

| 变量 | 说明 | 示例（凯西项目） |
|---|---|---|
| **我方主体名** | 正式文本里指代本方时用的名称（品牌名 / 公司简称）。一律不用「我们」。 | 沃橙 |
| **对外语域** | 是否面向中文官网 / 政企评审。决定走 `cn-website-copy.md` 的中文句法还是通用方案体。 | 中文官网 → 走中文句法 |
| **客户 / 甲方名** | 正文中的客户称谓，保持与合同一致。 | 凯西 |
| **产品与术语** | 该项目钦定保留的术语、年限写法。 | WorkBuddy、召唤、卡点、打通、5+ 年 |
| **交付语种与体例** | 中/英、是否双语、数字与单位写法。 | 中文、中文数字量词 |

不确定就问用户，不要默认套用上一个项目的主体名。

## 什么时候用

- 用户要求"改文风 / 去 AI 味 / 书面化 / 像一份正规方案汇报"。
- 用户逐条给出措辞意见，需要改文案并交付对照表。
- 用户要求审核文案、核对禁用词、统一自称与术语。
- 用户给出一份新版本文件，要求"做同样的文风修改"。

## 三条铁律

**铁律一：先看功能与语境，再判断原意，最后才动笔。**
三步递进，少一步就会改出"形态没变、功能变了"的错——标题改完长得还像标题，但已经不干标题的活了。

- **功能**：这段文字在这个位置干什么（标题？副题？图注？承诺？）—— 功能位决定改动边界。见 `references/edit-discipline.md` 第一节。
- **原意**：这句原本想说什么 —— 答不上来就别改。
- **动笔**：同义替换、把有力度原词换成平庸词，都属于减分。拿不准就保留原样，并在交付说明里讲明。

配套约束：**每一处改动都要能指出它对应哪一条规则；指不出来的，撤销，恢复原文。**
（落地方式：定改动集时加「病因」列，填不出来的条目直接删。）

用户的原始要求：**"我要的不是为了改而改，要贴切、精炼、有力。"**

**铁律二：结构层不动。**
标题、页码、页序、页面增删、交叉引用页码、配图、版式与 CSS 一律不改，只改文本节点的内容。
用户在别处调整过的页序与删页，不"好心"回滚。

**铁律三：每轮交付对照表。**
固定两件套：① 改好的文件（版本号递增）；② **逐页文字修改对照表**（格式见 `references/revision-log-format.md`）。
交付前必须校验：表中每条"改后"文案都能在新文件里命中。

## 文风标准（十二条）

1. **正规方案体，书面化。** 主语不省，一句一判断，语气有力但不刻意。
2. **术语用术语。** 行业词与产品词不替换成通俗说法（"召唤""卡点""打通""口径卡""留痕"）。
3. **精炼。** 一句话一个信息点；删掉"其实、比较、某种程度上、非常"这类空转修饰。
4. **力度来自事实。** 用数字、角色、动作说话，不靠形容词和排比堆煽动力。
5. **自称统一到项目主体名。** 正式文本不用「我们」这类指代不清的说法，一律使用当前项目确定的对外主体名（见上「项目变量」，如凯西项目用「沃橙」）。
6. **数字写成可核对的具体值。** 人数、比率、周期、阈值都给出具体数。
7. **主语明确到角色。** 写"大区经理""SFE""管理层"，不写"相关人员""大家"。
8. **结论在前，依据在后。**
9. **动词选准。** 「打通」的重点是"通"，「覆盖」讲的是范围，两者不可互换。
10. **保留原稿的专有写法。** 年限写"5+ 年"就不转成"5 年以上"；用户钦定的说法不动。
11. **先否定再肯定（"不是……而是……"）非必要不用。** 这类句式把"读者并没有的误解"先立起来再推翻，**当调味料用，不当主料**：默认直接说后半句；确有必要时全篇只准用 1 处（长稿不超过 2 处），**不要到处都用**。
    什么叫"必要"（三条全中）、什么算"没必要"、换皮怎么认，见 `references/banned-words.md` 的「用量条款」；`check_wording.py` 会统计全家族用量并报超支（输出项：`翻案腔用量`）。
12. **报告体裁不用隐喻与第一人称（2026-10-20 新增，用户点名）。** 调研、分析、推演、诊断类文档按严谨报告体处理：
    - **不写**「站在 X 的椅子上想问题」「手上有什么牌」「不能动的柱子」「摊开账本」「这条腿没长出来」「病根」「扎手的数据」这一类场景化、器物化、身体化比喻。抽象处境要直说（约束条件 / 可用工具 / 失效原因 / 结构性短板）。
    - **不用第一人称议论**：「我的自问」「我看过的案例」「我要的不是……」一律转为客观陈述（需要回答的问题 / 已有案例显示 / 目标不是……）。角色扮演式的视角设定只写在文首一行说明里。
    - 引用原文（媒体评论、受访者原话、行业论断）中的比喻**不改**，那是证据。只改作者自己的措辞。
    - 完整清单与逐条替换见 `references/banned-words.md` 的「隐喻清单」与「报告体裁的第一人称」两节。
13. **正向表达优先（2026-10-21 新增）**：
    - **动作优先**：用"完成 X""交付 Y""对齐 Z"，不用"积极推进""努力实现""大力开展"
    - **结果可见**：数字 + 角色 + 具体动作，不写"相关人员""团队成员""大家"
    - **承认边界**：不装全知，说"已完成 A、待确认 B"而非"完全满足""全面覆盖"
    - **保留力度**：有力度的原词（打通/召唤/卡点/留痕/实战）不换成平庸书面语
    - 完整范式与案例见 `references/positive-expression.md`

细节规则与句式改造对照见 `references/style-rules.md`；禁用词与慎用词分级见 `references/banned-words.md`。

## 个人用词偏好补充（2026-10-27）

- **避免使用“接住”及其引申表达。** 公主不喜欢“业务能不能接住”“客户能不能接住”等说法。该词偏口语、边界含糊，容易削弱正式表达的力度。
- 根据具体语境改为更准确的动词：**承接需求、进入流程、落到业务、被团队采用、由客户团队接手、持续使用、完成迁移、形成应用**。不要机械替换，先判断句子真正要表达的是接受、执行、使用还是交接。
- 适用范围包括公众号推文、方案、汇报、培训材料和标题；引用原话时可保留，但作者自行表达时默认不用。

## 中文官网文案句法（2026-11-12 新增，用户点名）

**官网/官网性质的首屏、公司简介、团队段，走 `references/cn-website-copy.md` 的中文句法，不走英文站语感。**

用户原话：“你要看中文的网站，不要学英文的表达方式，越学越AI。”
实测 20 家中文站（致远、东软、金蝶、浪潮、软通、汉得、讯飞、商汤、智谱、火山引擎、神策、钉钉、用友、海康、腾讯云等）后的硬规则：

1. **H1 用动宾直说或品类名词短语。** 不写隐喻（“让 AI 长在业务里”）、不用 `Where/For` 起句、不写三个并列形容词。
2. **副标题 = 范围列举 + 谁得到什么。** 火山引擎范式：“模型、工具、应用到云底座，企业 AI 一站构建”。不超过 25 字。
3. **数据条按证据类别分组**（年限 / 交付数量 / 真实影响人数 / 资本或资质背景），不按业务线分组；两个同类指标不可并排。
4. **讲历史用“年限 + 沉淀 + 名词”**，把过去压成一个可命名的资产；不写“那套…现在是…的一部分”，不写“从…走到…再走到…”。
5. **团队段只有三种写法**：规模（占比）、出身（哪些公司的什么岗位）、年限。不写三个“懂”、不写“不转包/不断层”、不写“从第一次诊断到最终验收”。
6. **官网正文禁用口语指代词**（那套 / 那时 / 它 / 这个），指代应接近零。
7. **“不转包”不是亮点**（用户 2026-11-12 点名）：行业默认，写出来反而暗示行业普遍转包。
8. **对偶金句按 AI 味处理**：“进得了业务，留得下能力”这类字数对齐、概念抽象、换个主语还成立的句子，一律重写。

逐条句式红线、可抄的例句、交付前 7 项自检见 `references/cn-website-copy.md`。

## 改动分层（决定能不能批量）

| 层 | 内容 | 处理方式 |
|---|---|---|
| 机械层 | 禁用词、自称、术语统一、图注格式 | 可批量替换，逐条记录命中次数 |
| 判断层 | 口语化句式、主谓残缺、逻辑跳跃、标题与正文重复 | **必须逐条读上下文重写**，每条给出理由 |

判断层是这份工作真正值钱的部分。机械层替换几分钟能跑完，判断层必须一页一页看。

## 工作流程

1. **通读全文**。若输入是 HTML 幻灯片，先用 `cheche-html-deck-edit` 的 `extract_deck_text.py` 抽成按页 Markdown 再读。
2. **定改动集**。写成表：`页｜位置｜原文｜改后｜类别｜理由｜病因`。机械层与判断层分开列；每条都要能回答"原文想说什么"，拿不准的**留白**并在交付里说明。
   - 先给每个待改元素定**功能位**（标题 / 副题 / 图注 / 承诺…）—— 功能位不同，改动边界不同。
   - **「病因」列 = 这条改动对应哪一条规则。填不出来的条目直接删掉，不要改。**
   - **【新增拦截】每条改动过一遍"有没有把有力度原词换成平庸词"**：
     - 若原词是术语/产品词/用户钦定说法（如"打通""召唤""卡点"） → 不改
     - 若功能位是标题/承诺且改后损失冲击力 → 恢复原文
     - 若把动作动词换成空转表达（"完成"→"积极推进"） → 撤销改动
   - 表定完过一遍"改后还干不干原来的活"：标题是否还是标题、图注是否还是图注。
3. **执行**。
   - 纯文本（md / txt / docx）：直接改。
   - HTML 幻灯片：交 `cheche-html-deck-edit` 落盘，不要在本技能里手改 HTML。
4. **校验**。`python scripts/check_wording.py <file> --brand <项目主体名>` 扫禁用词与自称。
   看两项：禁用词是否有漏改；**翻案腔总用量是否超支**（非必要不用，短稿 ≤1 / 长稿 ≤2，见 `banned-words.md` 用量条款）。
5. **出对照表**。用 `scripts/gen_revision_log.py` 生成，**合并多轮改动为一份净结果表**并跑强校验；
   纯文字改稿用 `--pairs` 给一份手写清单即可，不必等 `changes.json`。格式规范见 `references/revision-log-format.md`。

## 改动落地时的版式约束

改文案会撑破固定版式，这是本类任务最常见的翻车点。**动手前先量宽度**：

- 可用宽度 ≈ 下一个兄弟元素左边界 − 目标元素左边界；中文按 1 字 ≈ 1 个 em 估算可放字数。
- **同类并列元素必须等长**——一组横向组名/标签/描述行，任何一条比别人长，即使不折行，视觉节奏也垮了。
- 加长后必须**截图与原稿并排比对**（折行不报重叠，但一眼就露馅）。

完整版式红线与验收清单见 `cheche-html-deck-edit/references/workflow-html-deck.md`。

## 脚本

- `scripts/check_wording.py` —— 扫 A/B/C 词表、自称、可疑句式；支持 `.html / .md / .txt`。
  用 `--brand` 传入当前项目的我方主体名（可逗号分隔多个）；不传则只报「我们 / 咱们」并提示。
- `scripts/gen_revision_log.py` —— 生成《文字修改对照表》并做**交付前强校验**。**本技能自带，不依赖别的技能。**
  两个输入口：`--changes changes.json`（HTML 改稿时由 `cheche-html-deck-edit` 产出）、
  `--pairs 改动清单.txt`（纯文字改稿时手写，一行一条：`页码 || 位置 || 原文 || 改后 || 说明`）。
  多条 `--changes` 按顺序**链式归约**（A→B、B→C 合成 A→C），输出净结果；
  `--verify 新文件` 校验表中每条「改后」文案能否命中，未命中即报错。格式规范见 `references/revision-log-format.md`。
